## 2026-10-07 — Developer news strip: research and design

**What changed:** Added the spec `docs/features/developer-news.md` and the v1 interactive mockup `docs/design/developer-news/mockup.html` for a developer news strip on the login page. No extension code changed yet.

**Why:** We want to announce development-tool news (clio releases, tips, webinars, breaking changes) to extension users without shipping an extension release for every item, and without taking room from the login form.

**Decision:** A 32 px always-visible strip under the profile row with a collapsible panel, rather than a bell icon or a full banner. Research across Facebook, X, Google, GitHub and changelog widgets showed the same two-level pattern; placement inside the task flow beats a stronger colour, and the signal must appear only for new items to avoid badge blindness. The feed is a static JSON file (GitHub Pages) fetched by the service worker with a 6 h TTL: it is data, not code, so it complies with MV3 remote-code rules and needs no new permissions.

**Shell surface (same day):** Added `shell-mockup.html` and the "Shell surface" and "Shared state model" sections of the spec. Inside Creatio people are working, so news escalate in levels: an 8 px dot on the Clio satellite button (clears on menu open, decays after 7 days or 10 loads), a `What's new` row on top of the menu that opens a glass flyout, and a one-time peek card only for critical items. Read state is shared through `chrome.storage.sync`, so reading on the login page clears the dot in Shell. The planned code moved from `login/news.js` to `src/news/` inside the `content.js` bundle, because `content.js` already runs on login pages and one module can serve both surfaces without duplicating validation in the non-bundled `login.js`.

**Trending news and media (same day):** Two new requirements in the spec. (1) An administrator can mark an item `trending` with a window: `hours` counted per user from first display, `until` as an absolute UTC end, or both (earliest wins). Outside the window the item stops producing any unread signal but is not marked read, so extending the window brings it back. Trending and `critical` are mutually exclusive: a breaking change must never go quiet on its own. (2) An item may carry one optional `media` block: an image from the feed host or a YouTube video by `videoId`. Media shows only in the expanded panel/flyout, loads on first open through the service worker as a `data:` URL (page `img-src` CSP on self-hosted instances would block a plain `<img>`), and YouTube is a poster that links out instead of an embedded `<iframe>`, which would depend on the host's `frame-src` CSP and load third-party cookies into the CRM page. Both mockups show the Trending chip, a trending-window-over scenario, an image card and a YouTube card.
